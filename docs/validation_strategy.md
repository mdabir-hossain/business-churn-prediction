# Validation Strategy

## Status

This Phase 4 document defines the validation design that should be implemented before any controlled model evaluation is reported. It does not contain model results.

No models were trained, no notebook cells were executed, and no metrics were generated while creating this strategy.

## Current Validation State

The existing notebook uses a single stratified train/test split:

- `test_size=0.2`
- `random_state=42`
- `stratify=y`

This is a reasonable early-stage baseline, but it is not yet enough for a polished portfolio project. The project still needs a clearly defined prediction setup, leakage-safe preprocessing, and saved metric provenance.

## Why Stratification Is Useful

Churn data is typically imbalanced: non-churners often outnumber churners. Stratification helps keep the target-class proportions similar in train and test splits, reducing the chance that a small or unlucky split under-represents churn cases.

Stratification does not solve leakage, temporal mismatch, or business-threshold design. It is a split-quality safeguard, not a full validation strategy.

## Cross-Validation Plan

Cross-validation may be added in Phase 5 to make model comparison less dependent on one random split.

Recommended approach:

- use stratified cross-validation for early tabular model comparison
- fit all preprocessing inside each fold
- report mean and variability for key metrics
- keep a final holdout test set if enough data is available

Cross-validation should not be used to tune and report on the same data without a clean final evaluation design.

## Temporal Validation Consideration

If event dates, billing-cycle dates, account extract dates, or churn dates become available, temporal validation may be more realistic than random splitting.

Temporal validation is preferable when the model will be used prospectively, because it tests whether patterns learned from earlier customers generalise to later customers.

Possible temporal design if dates exist:

- train on earlier billing periods
- validate on a later period
- test on the latest held-out period
- compute features only as of each scoring date

The current dataset columns inspected in the audit do not include explicit dates, so temporal validation is not yet implementable without additional data.

## Preprocessing Rules

All learned preprocessing must be fitted only on training data or training folds.

Required rules:

- one-hot encoders must be inside a fitted pipeline
- imputers, scalers, encoders, and learned binning must be inside train-only pipelines
- full-dataset `pd.qcut` must not be used before splitting
- target and identifier columns must be removed before feature preprocessing
- feature availability must match the proposed scoring moment

Deterministic row-level feature engineering may be applied before splitting only when it uses fields known at scoring time and does not learn thresholds or distributions from the full dataset.

## Metrics To Use Later

Accuracy alone is not enough for churn because the classes are imbalanced and the business cost of mistakes is asymmetric.

Recommended later metrics:

- ROC-AUC for ranking quality across thresholds
- PR-AUC for churn-class performance under imbalance
- precision for the churn class
- recall for the churn class
- F1 for the churn class
- confusion matrix
- lift/gains or top-decile capture
- calibration if probabilities are used for ranking or action
- threshold/cost curve
- business summary metrics based on explicit cost and capacity assumptions

Do not report any metric until it has been generated by a controlled, documented run and saved with provenance.

## Threshold Selection

The default 0.5 threshold is rarely the right business choice for churn. Threshold selection should reflect:

- retention team capacity
- cost of contacting or incentivising customers
- value at risk
- expected false-positive cost
- expected false-negative cost
- tolerance for customer fatigue
- operational constraints

Threshold analysis should be documented as a decision-support exercise, not as proof of causal impact.

## Model Comparison Principles

Future model comparison should include:

- a simple baseline
- logistic regression as an interpretable benchmark
- tree-based models if appropriate
- consistent preprocessing across models
- cross-validation or a documented validation split
- final holdout evaluation only after modelling choices are fixed

Model selection should prioritise business usefulness and robustness, not just the highest headline score.

## Provenance Requirements

Every future metric artifact should record:

- dataset path or dataset version
- whether the data is public-safe or local-only
- split strategy
- random seed
- preprocessing steps
- model family and parameters
- threshold used
- date generated
- command or notebook used
- limitations and known leakage assumptions
